## 1. The one thing M1.6 must prove

M1.0–M1.5 built a real dive loop — generate, salvage, throw, extract, quota, wipe — but the player still **boots straight
into a debug harness**: a Start button bolted onto the config rail, an auto-`SellScreen` as the only "between-runs" beat, and
the knob menu in everyone's face on the first screen. **M1.6 gives the game a *surface*: you boot to a real Main Menu, stage
in a walkable Hub between runs where you sell your haul and spend money at a Shop, and *depart* into dives from there — and the
debug controls move out of the player's face into a P-key tabbed panel.** This is the iteration that makes THE FAR YARD read
as a game rather than a test bench, and lays the Hub that every later meta system (upgrades, NPCs, Cyrus, debt) hangs off.

## 2. Scope guardrails (what M1.6 is and is NOT)

- **Greybox, exactly as M1.1–M1.5.** The Main Menu and Hub are default-theme/greybox: a `Control` menu and a small top-down
  greybox room (reusing the existing `Player` + the dive's interactable pattern — a shop terminal and a departure portal as
  greybox `Area2D` interactables). No authored art, no new bands, no generator change.
- **The all-off `RunConfig` default stays the permanent baseline control** (determinism fp = `e943ac9c8bc1`). M1.6 is a
  **structural / meta / UI** iteration — it does **not** add gameplay *lever* knobs and does **not** touch band generation, so
  the fingerprint must stay byte-identical and the **89-knob count is expected to hold** (M4 *regroups* the existing knobs into
  tabs without adding/removing any; `has_full_coverage()` + the 89-count tests must still pass).
- **The Shop sell path REPLACES the auto-`SellScreen`** (Director-ratified). Selling now happens at the Hub Shop; `SellScreen`'s
  sell logic (`GameState.sell_banked_junk`) is reused/absorbed, not duplicated. **Buying is new** — a minimal greybox catalog,
  spending `Money`. If purchases persist (owned upgrades/items), that is a **deliberate save-schema bump** (META v3→v4 +
  migration step + QA fixture), surfaced — not a silent change.
- **The dive clock is dive-only.** `DiveClock` (K4 timer) must **not** run in the Menu or the Hub. The clock lives in the
  dive scene only; entering the Hub neither starts nor ticks it (Director-locked: "the hub should not run the clock").
- **App flow = Main Menu → Hub ⇄ Dive** (Director-ratified). A new `main_menu.tscn` becomes the app entry
  (`run/main_scene`); `main_game.tscn` becomes the **dive-only** scene; runs return to the Hub. Scene transitions go through a
  small **app/scene router** (M0 defines the mechanism — `change_scene_to_file` vs. a root state-switcher; Phase 2 resolves).
- **Run-state vs. meta-state boundary holds** (`game_state.gd`). The Hub reads **meta** (Money, banked haul, owned purchases);
  it never holds run-state. Money/purchases are meta; the in-dive haul is run-state banked at a gate exactly as today.
- **NOT** in M1.6: new bands/art, a generator change, real enemy AI, new dive mechanics, NPC dialogue/Cyrus, the debt system,
  or balancing. `run_ended` arity stays locked; telemetry stays additive (`data` fields / new signals only).

## 7. Open risks to resolve in Phase 2/3 (per-task designs author these; fresh-eyes/Director ratify)

- **Scene-router mechanism (M0):** `get_tree().change_scene_to_file()` between three top-level scenes (Menu/Hub/Dive) — simplest,
  but each transition tears down state; how does the Hub survive a dive (rebuild from meta each return, since the Hub holds no
  run-state — likely fine)? Vs. a persistent root `App` node that swaps children (keeps autoloads + a stable HUD/debug overlay
  mount). Where does the **P-key debug overlay** live so it's available in *all three* states (a `CanvasLayer` on an autoload /
  root, vs. re-instanced per scene)? Resolve the mechanism before M1/M2 build against it.
- **Buy-economy shape (M3):** what is buyable in greybox — **consumables** (one-shot, non-persistent → no save bump) vs.
  **persistent upgrades** (owned across runs → save bump)? Recommend a **minimal persistent catalog** (e.g. 2–3 greybox
  upgrades) to exercise the meta-spend loop, accepting the META v3→v4 bump — but this is a **fun/scope call for the Director**.
  Price/effect values are configurable-not-balanced (greybox), authored as `.tres` by `game-director-designer`.
- **SellScreen retirement (M2/M3):** `SellScreen` currently auto-presents on `run_ended` and owns the quota-outcome readout +
  the web "Export telemetry" button + the roguelite-wipe routing (`pending_wipe`→`wipe_meta`). Retiring it means **re-homing
  all three**: the sell tally + quota line + wipe routing move into the Hub-return / Shop beat, and the telemetry-export button
  needs a new home (Shop UI? a Hub terminal? the debug menu?). Phase 2 must inventory every `SellScreen` responsibility so none
  is dropped. (This is the riskiest seam in M1.6.)
- **Where does selling happen — auto on return, or only at the Shop?** Director chose Shop-as-sell-place; confirm the haul is
  **held banked** on hub-return and only converts at the Shop (so you can see your haul before selling), vs. auto-sold on
  entry. Recommend: held → sold at the Shop (gives the Shop a purpose + matches "walk to shop = sell"). Phase 2 / Director.
- **Hub layout & interactables (M2):** room size/shape (reuse a greybox piece or a bespoke small room?), portal vs. shop
  placement, the interaction-prompt reuse (the L4-fixed `interaction_prompt` + the `interact`=F action — does the Hub reuse the
  dive's interactor wholesale?). Does the player's twin-stick/mouse aim do anything in the hub (probably movement only)?
- **Debug-menu tab taxonomy (M4):** the exact tab set + which section lands in which tab (proposed: Hazards / Level Gen /
  Timer & Quota / Vision / Exposure & Return / Throw & Camera / Meta). The current `r4_` section **mixes maze-branch knobs and
  vision/fog knobs** — M4 must **split** them (Vision = `r4_vision_radius`/`r4_vision_tighten_per_depth`/`r4_fog_enabled`/
  `r4_lost_proxy_threshold`; the maze-branch knobs stay in Level Gen) **without** changing the underlying `r4_` field names or
  the 89-knob coverage. Does the P-overlay pause the dive while open (recommend yes in-dive, no-op in menu/hub)?
- **Main-menu Continue/New semantics (M1):** "New Game" on an existing save — confirm it **wipes meta** (with a confirm
  prompt?) vs. refuses; "Continue" disabled when no save exists. First-run telemetry-consent (G6) currently lives over the
  `main_game` menu — re-home to the Main Menu.
- **`run/main_scene` + CI (M0):** confirm `tools/ci_smoke_test.gd` and the headless test scenes don't hard-assume
  `main_game.tscn` is the entry (they likely load scenes directly — verify, adjust if needed).
