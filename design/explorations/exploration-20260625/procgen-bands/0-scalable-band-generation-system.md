# Scalable Band-Generation System — Architecture Exploration
**Category:** Cross-cutting system / architecture
**Date:** 2026-06-25

> Architecture exploration only. Pseudocode is illustrative against the real as-built APIs; no production code, no contract widening, no branch. The goal is one model that produces (a) the bands that already exist (the linear/branchy socket spine), (b) the 19 explored archetypes/principles/flavors **with their modifications**, and (c) bands we haven't designed yet — so that adding a band, or a layout flavor, is **mostly data + small composable stages**, not a new bespoke generator. The non-negotiable is the seed-reproducibility contract enforced by `tests/test_bandgen_determinism.gd`. This doc mirrors the shape of the companion [`0-scalable-opposition-system.md`](../hazards/0-scalable-opposition-system.md): a data descriptor + composable stages + a determinism/parity contract.

## The problem

The 19 sibling explorations surfaced a clean **three-layer matrix**:

- **Base archetypes** (groups A–C: discrete rooms, hub-and-spoke, open field, archipelago, organic caverns, dense maze, grid) — standalone *layouts*.
- **Organizing principles** (group D: radial, lane-based, layered/tiered, asymmetric entry/exit) — *reshape* any archetype.
- **Generation flavors** (group E: symmetry, density-gradient, verticality fakes, set-piece injection, wear/decay) — *apply on top of* any archetype.

The combinatorics are the point: a *Critical-path + Radial + Set-piece* band and an *Open-field + Density-gradient + Wear* band are both legitimate authored bands, and the GDD wants **bands 1–4 each a distinct biome with its own ruleset** (TDD M3/M4, §"Procedural band assembly"). A bespoke generator per band, or one ever-growing config blob with a branch for each idea, does not scale: every new band or flavor would re-implement connectivity, depth grading, determinism, and the opposition handoff by hand.

Three facts from the explorations make a single config blob impossible:
1. Some archetypes need a **second generation backend** — organic caverns (cellular automata) and full tile-mazes have *no pieces and no sockets*, so they cannot ride the socket-assembly loop ([b3-organic-caverns](b3-organic-caverns.md), [c1-dense-maze](c1-dense-maze.md)).
2. Open-field needs a **scatter/poisson pass** — genuinely new placement code beyond the piece placer ([b1-open-field-with-cover](b1-open-field-with-cover.md)).
3. Every reshaping/flavor pass must **still guarantee a walkable entry→exit path** under the dive clock — connectivity is a cross-cutting invariant, not a per-archetype afterthought.

What we want: **bands authored in `.tres`**, generated by **discrete composable stages** that each read the band's descriptor and mutate a shared build, every stage seed-deterministic, with one clean seam where the finished band hands placement context to the opposition spawner.

## What exists today (as-built)

The shipped generator (`systems/bandgen/band_generator.gd`, ~520 lines) is genuinely good *within its scope*, and several patterns are load-bearing keepers:

- **Socket-piece assembly.** `generate(seed, cfg, catalog, rc) -> Band` is a pure function: place an entry piece at the origin, repeatedly pick a frontier socket, weighted-draw a compatible piece (`_weighted_pick_index` over an integer cumulative table), mate it flush (`_alignment_offset`, integer-cell), reject overlaps (`band.fits`), grow to `target_piece_count`. Whole-band retry with a hash-combined derived seed (`_derive_seed`) on undersize.
- **Integer-cell determinism.** All layout math is `Vector2i`; pixels appear only at instance time. `Band.fingerprint()` is an ordered `piece_id@offset#mated` sha256 — the byte-identical acceptance bar.
- **Dormant extension seams already in place.** `_find_mate_socket` runs a predicate chain `dir_ok AND width_ok AND tags_ok` where `_width_ok`/`_tags_ok` are true-stubs awaiting width/biome variance. `branch_chance` (and the R4 depth-scaled fork curve) is the linear↔branchy lever, defaulting to a pure linear spine. `loop_back_count` is reserved for a cyclic pass.
- **A clean post-layout stage stack that reads only geometry, never sockets.** `SocketSealer` (geometry-keyed, RNG-free, fingerprint-preserving) walls every floor cell facing void. `DepthGrader` assigns `depth_index`/`depth_norm`/`dist_to_gate` by BFS over **FLOOR-cell 4-adjacency**. `JunkPlacer` populates loot on a **local RNG sub-stream** (`band.resolved_seed` ⊕ `_JUNK_SALT`) so loot rolls never perturb the layout stream.
- **Config-as-Resource.** `BandGenConfig.tres` carries the knobs; `RunConfig` carries the iteration levers, all-off default = byte-identical baseline.

**Where it won't stretch:**
- **Single backend.** Everything assumes authored rectangular `ZonePiece` scenes mated at sockets. No CA, no scatter, no tile-grid backend.
- **No per-band profile.** There is exactly *one* `bandgen_config.tres` and one `piece_catalog.tres`. `data/bands/` is empty (`.gitkeep` only) — **a "band" today is the global config, not a content resource.** Bands-as-biomes do not exist as data yet.
- **No flavor compositing.** A flavor (density gradient, symmetry, wear) has nowhere to live: there is no post-layout *reshape/decorate* phase between layout and grading, only the seal pass.
- **No archetype selection.** The linear/branchy spine is the only topology; hub-and-spoke, radial, lanes, grid are unreachable from data.

This is exactly the wall the explorations hit: nearly every one ends with "needs a new placement mode / second backend / a pass the generator doesn't have."

## Prior art (researched, cited)

**Layered / staged generation (skeleton → carve → decorate → populate).** Minecraft's pipeline splits cleanly into a **Generation** phase (base terrain + biomes) and a **Population** phase (structures first, then decoration), each stage refining a shared world state ([How Minecraft Terrain Generation Works](https://cybrancee.com/blog/how-minecraft-terrain-generation-works/), [Minecraft Wiki — World generation](https://minecraft.wiki/w/World_generation)); academic underground generators (PLUME) likewise generate a graph "skeleton" then layer carving and population on top ([PLUME, arXiv 2508.20926](https://arxiv.org/html/2508.20926v1)). **Transfers directly:** our `SocketSealer → DepthGrader → JunkPlacer` is *already* a population pipeline; the proposal generalizes the *generation* half into the same staged shape.

**Data-driven biome = graph + room pool (Dead Cells).** Dead Cells authors a per-biome **concept graph** (length, number of special tiles, how labyrinthine, entrance-to-exit distance) and a **room pool dedicated to that biome** (prison rooms never appear in sewers); the generator walks the graph and tries random rooms from the biome pool until one satisfies the node's constraints ([Deepnight — Level Design of Dead Cells](https://deepnight.net/tutorial/the-level-design-of-dead-cells-a-hybrid-approach/), [Dead Cells Wiki — Biomes](https://deadcells.wiki.gg/wiki/Biomes)). **This is almost exactly the BandProfile proposal**: a biome is *data* (a graph spec + a piece pool + spawn rules), not code. Spelunky's template-grid + chunk approach is the same family and is credited as Dead Cells' inspiration.

**Graph grammars / cyclic generation (Unexplored).** Joris Dormans' Unexplored composes dungeons from **cycles** (loops with a designed flow — lock-and-key, hidden shortcut), nesting them so a dungeon feels intentionally designed; it uses graph/tile grammars (~5000 find-replace rules in Ludoscope) ([Game Developer — Unexplored's Secret](https://www.gamedeveloper.com/design/unexplored-s-secret-cyclic-dungeon-generation-), [BorisTheBrave — Dungeon Generation in Unexplored](https://www.boristhebrave.com/2021/04/10/dungeon-generation-in-unexplored/)). **What transfers:** the *cyclic backbone* idea (our reserved `loop_back_count`) as one optional **principle stage**, giving loops/lock-and-key without random-scatter feel. **What doesn't:** a full grammar engine with thousands of rules — the TDD explicitly **rejects full grammar engines and pure-WFC master generation** (§"Procedural band assembly"). We borrow the *concept* (cycles as a reshape pass), not the machinery.

**WaveFunctionCollapse.** WFC shines when you need example-driven tile-adjacency *and* aesthetic complexity, but it brings overfitting, homogeny, and **connectivity** problems, and the literature recommends it as one stage in a *mixed* pipeline, not a universal master generator ([Combining Constructive PCG with WFC in Top-Down 2D, ResearchGate](https://www.researchgate.net/publication/348569324_Combining_Constructive_Procedural_Dungeon_Generation_Methods_with_WaveFunctionCollapse_in_Top-Down_2D_Games), [mxgmn/WaveFunctionCollapse](https://github.com/mxgmn/WaveFunctionCollapse)). **Verdict for us:** WFC is *overkill* as a band backend right now (our seams are 2-cell sockets, not rich tile adjacencies) — but the **socket predicate chain is already a constraint-satisfaction stub**, so if a future band wants WFC-style coherent interiors it slots in as one optional backend behind the same interface, not a rewrite. Defer, don't adopt.

**Net read:** adopt **Dead Cells' data-driven-biome model** (profile = backend + archetype graph + piece pool + spawn rules), structure generation as **Minecraft-style discrete stages**, keep our existing generator as the **default socket backend + first stages**, reserve **cyclic-grammar and WFC as optional later stages/backends behind one interface**, and **protect determinism** (none of the cited generators are seed-reproducible the way ours must be).

## Proposed architecture

### The band descriptor — `BandProfile.tres`

A new content Resource, `BandProfile extends Resource`, sibling to `JunkItem`/`OppositionDef`, authored in the inspector. **This is the thing `data/bands/` was always meant to hold.** One `.tres` per band-as-biome (Band 1 "Near", Band 2 "Alien", …). Illustrative schema:

```gdscript
class_name BandProfile extends Resource
@export var id: StringName                      # &"band_near" — stable; save/telemetry/audio
@export var display_name: String

# --- Which BACKEND builds the raw floor/occupancy ---
@export_enum("socket","cave","scatter") var backend: String = "socket"
@export var backend_config: Resource            # BandGenConfig | CaveBandConfig | ScatterConfig

# --- Base ARCHETYPE (topology the backend grows toward) ---
@export_enum("linear","branchy","hub","grid","lanes") var archetype: String = "linear"
@export var archetype_params: Dictionary = {}   # {"branch_per_depth":0.06,"spokes":4,...}

# --- Content the backend draws from ---
@export var piece_pool: PieceCatalog            # the biome's dedicated pieces (Dead Cells model)
@export var tileset: TileSet                    # palette/silhouette for band contrast (TDD §9)

# --- ORGANIZING PRINCIPLES (ordered post-layout reshapes) ---
@export var principles: Array[Resource] = []    # [RadialPrinciple, LanePrinciple, ...]

# --- FLAVOR passes (ordered decorate passes on top) ---
@export var flavors: Array[Resource] = []       # [DensityGradient, Symmetry, WearDecay, SetPieceInject]

# --- Depth + population ---
@export var depth_curve: DepthCurve             # reward/tier-by-depth (already exists)
@export var junk_catalog: JunkCatalog
@export var opposition_deck: Array[OppositionDef]  # the seam to the opposition Director

# --- Band-depth placement (bands-as-biomes ordering) ---
@export var band_depth: int = 1                 # which dive tier; drives Instability I
```

The `*_params` / principle / flavor entries are the **`spawn_ctx`/`params` pattern** the opposition doc promotes to data, applied here: each stage reads only its own keys, exactly as the K5 hazards read `initial_dir`/`phase_salt`.

**Worked example — existing band (today's baseline as data):**

```
id = band_greybox        backend = "socket"      archetype = "linear"
backend_config = bandgen_config.tres (target 12, branch 0.0, soft floor 80%)
piece_pool = piece_catalog.tres      principles = []     flavors = []
depth_curve = (current)   junk_catalog = (current)   opposition_deck = []   band_depth = 1
```
With empty principles/flavors and the socket backend, this profile **reproduces the current band byte-for-byte** — the permanent control, mirroring the all-off `RunConfig` discipline.

**Worked example — a future band we haven't designed:**

```
id = band_drowned_vault  backend = "cave"        archetype = "branchy"
backend_config = cave_config.tres (fill 45%, smooth 4, min_region 60)
principles = [ RadialPrinciple(pole = deepest, danger_by_radius = true) ]
flavors    = [ DensityGradient(pockets=3, contrast=0.7),
               WearDecay(state="flooded"),
               SetPieceInject(defs=[archive_room], max=1, min_depth_norm=0.6) ]
depth_curve = steep   opposition_deck = [ambusher, burrower, gas_field]   band_depth = 3
```
Same engine, entirely different band — **all in data.**

### The generation pipeline — discrete composable stages

`generate(profile, seed) -> Band` is a fixed ordered list of stages. Each stage is a small `RefCounted` with one method `apply(build, profile, seed)`, reads the profile, mutates a shared `BandBuild`, and is seed-deterministic. The orchestrator is ~30 lines:

```gdscript
func generate(profile: BandProfile, seed: int) -> Band:
    var build := BandBuild.new()                       # shared mutable state
    var backend := _backend_for(profile.backend)       # socket | cave | scatter
    backend.build_layout(build, profile, seed)         # STAGE 1: raw floor + entry + occupancy
    _archetype_for(profile.archetype).shape(build, profile, seed)  # STAGE 2 (socket backend: this IS the grow loop's topology)
    for p in profile.principles:  p.reshape(build, profile, _stage_seed(seed, p))   # STAGE 3: principle overlays
    for f in profile.flavors:     f.decorate(build, profile, _stage_seed(seed, f))  # STAGE 4: flavor passes
    _connectivity_guarantee(build)                     # STAGE 5: carve/verify entry→exit (invariant)
    var band := build.to_band(seed)
    SocketSealer.new().seal_unused_sockets(band)       # STAGE 6: seal void (existing)
    DepthGrader.new().grade(band)                      # STAGE 7: depth axis (existing)
    DepthGrader.new().compute_return_distance(band)
    return band                                         # population (JunkPlacer/opposition) downstream, unchanged
```

**The existing generator becomes the default `socket` backend + the `linear`/`branchy` archetype.** No algorithm change: `BandGenerator._generate_once` *is* `SocketBackend.build_layout` + the linear/branchy archetype's `shape`, reading `profile.backend_config` (a `BandGenConfig`) instead of a global. Stages 6–7 already exist and already read **only geometry**, so they work for *any* backend.

**Per-stage seeding.** Each principle/flavor stage gets a derived sub-seed via the existing hash-combine (`_stage_seed(seed, stage) = _derive_seed(seed, stage.salt)`) — the same trick `JunkPlacer` uses to keep its rolls off the layout stream. A stage that *only* decorates off-stream (junk density, cover scatter) **never moves `fingerprint()`**; a stage that genuinely reshapes the layout (radial re-anchoring, lane partition) **legitimately moves it**, exactly as R4/J4 config legitimately move it under the `(seed + config)` contract.

### Multi-backend behind one interface

Three backends implement one duck-typed contract — `build_layout(build, profile, seed)` populating `build.floor_cells` (band-global), `build.occupied`, `build.entry`, and either piece records (socket) or a raw floor set (cave/scatter):

| Backend | Builds | Resolves the explored flag |
|---|---|---|
| **`SocketBackend`** (default, exists) | authored `ZonePiece` rects mated at sockets | rooms, hub, grid, lanes, critical-path, set-pieces |
| **`CaveBackend`** (new, ~120 lines) | seeded fill% → N CA smoothing passes → keep largest flood region | **resolves the "second backend" flag** for organic caverns ([b3](b3-organic-caverns.md)) and tile-mazes ([c1](c1-dense-maze.md)) |
| **`ScatterBackend`** (new, ~80 lines, or composes onto Socket) | one large arena floor + poisson-disk cover stamping on a `_COVER_SALT` sub-stream | **resolves the scatter flag** for open-field ([b1](b1-open-field-with-cover.md)) |

The crucial design win, already proven by the explorations: **all three feed the SAME downstream stages.** `SocketSealer`, `DepthGrader`, and `JunkPlacer` consume only **FLOOR-cell 4-adjacency** — they never touch sockets — so a CA cave grades depth by hops and scatters loot *unchanged*, and a scatter arena is just a big-area node. The backend produces the floor; everything after the backend is shared. CA/scatter pieces become "synthetic `PlacedPiece`s" (one per flood-region, or one arena) carrying `floor_cells`, so the `Band` data shape is identical regardless of backend.

### Composition proof (the heart of "scalable WITH modifications")

Six explored ideas, assembled from the **same stage list** with different profile data and **zero new bespoke generator** beyond the two new backends:

| Explored band | Backend | Archetype | Principle stage(s) | Flavor stage(s) | New code? |
|---|---|---|---|---|---|
| **Critical-path + side rooms** ([a4](a4-critical-path-side-rooms.md)) | socket | branchy | — (spine + greedy detours via branch curve) | — | none |
| **Critical-path + Radial + Set-piece** | socket | branchy | `Radial` (danger/loot by radius) | `SetPieceInject(vault @ deep)` | reuses `SetPieceInject` |
| **Open-field + Density-gradient** ([b1](b1-open-field-with-cover.md)+[e2](e2-density-gradient.md)) | scatter | linear (1 arena node) | — | `DensityGradient` drives cover+junk scatter count | `ScatterBackend` + `DensityGradient` (each written once) |
| **Organic caverns + Wear/decay** ([b3](b3-organic-caverns.md)+[e5](e5-wear-decay-state.md)) | cave | branchy | — | `WearDecay(flooded → blocks routes, opens breaches)` | `CaveBackend` + `WearDecay` |
| **Grid / city blocks + Symmetry** ([c3](c3-grid-city-blocks.md)+[e1](e1-symmetry.md)) | socket | grid | — | `Symmetry(mirror)` | `Grid` archetype + `Symmetry` |
| **Layered / tiered** ([d3](d3-layered-tiered.md)) | socket | linear | `Layered(tiers=[front, deep])` filters piece pool by `_tags_ok` on `depth_norm` thresholds | per-tier flavor | activates the dormant `_tags_ok` predicate |

Each reusable stage (`Radial`, `DensityGradient`, `WearDecay`, `Symmetry`, `SetPieceInject`, `Layered`) is written **once**, then reused across any profile — the same "add a band = data + maybe one new stage" claim the opposition doc makes for "add an opposition = data + maybe one new component." **Set-piece injection and wear/decay are the cheapest wins** because they ride the existing socket/sealer machinery with no new backend ([e4](e4-set-piece-injection.md), [e5](e5-wear-decay-state.md)).

### Determinism & connectivity contracts

**Determinism** is preserved by construction and remains enforced by the real tests:
- The orchestrator passes `seed` into the backend; the backend reseeds the autoload (`RNG.seed_from(seed)`) exactly as `_generate_once` does today. The socket backend's RNG draw site/order is **unchanged**, so an empty-principle/flavor `band_greybox` profile produces the **byte-identical** `fingerprint()` that `tests/test_bandgen_determinism.gd` already pins (its same-seed→same-fp, diff-seed→diff-fp, connectivity, overlap-free, and seal-fingerprint-invariance assertions all transfer to the orchestrated path as the regression bar).
- Every principle/flavor stage either runs **off-stream** (a local `RandomNumberGenerator` seeded from `seed ⊕ stage.salt`, the `JunkPlacer._JUNK_SALT` pattern — never moves the layout fingerprint) **or** is a documented layout-affecting config under the `(seed + config)` contract (moves the fingerprint *deterministically*, like R4/J4). No stage touches the global RNG out of order.
- CA/scatter backends must use **order-stable iteration** (sorted flood regions, sorted sample order) so their floor sets are seed-reproducible — the one genuine new correctness gotcha, called out in [b3](b3-organic-caverns.md)'s open questions.

**Connectivity** is promoted from a socket-backend side-effect to an **explicit Stage 5 invariant** that runs after *every* reshaping/flavor pass: flood-fill from `entry` over FLOOR-cell 4-adjacency (the exact `is_band_connected` check the generator already ships); if any floor is unreachable, **carve a minimal connector** (or, for socket bands, the stage is a no-op assert since assembly guarantees it). This directly answers the recurring exploration flag — *every route-altering idea (decay-blocked routes, archipelago gaps, dense mazes) must still guarantee a findable entry→exit path under the dive clock.* Because it runs **after** flavors, a `WearDecay` pass that blocks a corridor cannot strand the player: Stage 5 re-verifies and breaches if needed.

### Handoff to oppositions

The seam is clean and one-directional. After Stage 7, the `Band` carries everything the opposition spawner needs as **placement context**: per-piece `floor_cells`, `depth_index`/`depth_norm`/`dist_to_gate`, the entry/deepest anchors, and `band.resolved_seed`. The band generator **does not spawn oppositions** — it hands this context to the `OppositionDirector` from the companion doc, which walks pieces in a stable RNG-free order and spends an Instability-scaled credit budget per `profile.opposition_deck`. This mirrors the as-built `main_game.gd` flow where `_spawn_new_hazards` consumes the graded band. The `BandProfile.opposition_deck` + `band_depth` (→ Instability `I`) are the data that parameterize that handoff, keeping the two systems decoupled through data, not hard references.

## Per-band / per-layer fit table

| Existing band / explored group | Backend | Stages it needs | Fits cleanly? |
|---|---|---|---|
| **Current greybox band** (baseline) | socket | linear archetype only | Yes — the permanent control profile |
| **A — room/corridor** (a1–a4) | socket | linear/branchy archetype; hub = principle | Yes — native to today's generator |
| **B1 open field** | scatter | `ScatterBackend` + poisson cover | Yes, with new backend (genuinely new code) |
| **B2 archipelago** | scatter/socket | islands + gap connectors | **Partly** — gaps fight the connectivity invariant; needs explicit bridge carving in Stage 5 |
| **B3 organic caverns** | cave | `CaveBackend` + flood-keep | Yes, with new backend; downstream reused wholesale |
| **C1 dense maze** | cave (tile) | maze backend + bounded region | **Partly** — best as a *region inside* a band, not a whole band (legibility) |
| **C2 sparse labyrinth / C3 grid** | socket | maze/grid archetype | Yes — grid is a new archetype `shape`, no new backend |
| **D1 radial / D2 lanes / D4 asymmetric** | any | principle reshape stage | Yes — pure post-layout overlays |
| **D3 layered/tiered** | socket | `Layered` principle (activates `_tags_ok`) | Yes — but see Open Questions (overlap with bands-as-biomes) |
| **E1 symmetry / E2 density / E3 verticality / E5 wear** | any | flavor decorate stage | Yes — off-stream or documented layout-affecting |
| **E4 set-piece injection** | socket | `SetPieceInject` flavor (depth-gated draw) | Yes — cheapest win, rides existing machinery |

**Don't fit cleanly (called out honestly):** **archipelago gaps** and **dense-maze-as-whole-band** stress the connectivity invariant and legibility respectively — both want to be *bounded regions within* a band rather than a whole-band topology. **Verticality fakes** ([e3](e3-verticality-fakes.md)) are a *rendering/one-way-flow* convention layered on flat geometry, not a generation stage in the structural sense — it decorates but doesn't reshape the floor graph.

## Migration path

Phased, baseline-parity-preserving — never break the determinism fixture in one pass:

1. **Phase A (M1-cheap, no behavior change).** Introduce `BandProfile` + a thin `BandPipeline` orchestrator that, for a `socket`+`linear`+no-principle/flavor profile, calls today's `BandGenerator` unchanged. Author the **current band as `data/bands/band_greybox.tres`**. Acceptance: `test_bandgen_determinism.gd` fingerprints byte-match through the orchestrated path. This is the riskiest *correctness* step and the cheapest *code* step (mostly a wrapper + the descriptor Resource).
2. **Phase B (M1-cheap).** Add the **two cheapest flavor stages** that need no new backend — `SetPieceInject` and `WearDecay` — since they ride the existing socket/sealer machinery (strong effort-to-variety ratio per the README). Each ships off by default (empty `flavors`), so the control is intact.
3. **Phase C (M2).** Add the **`Grid`/`hub` archetypes** and the **principle stages** (`Radial`, `Lane`, `Layered`) as post-layout overlays on the socket backend — no new backend, real variety. This is where bands 1–3 start to feel distinct (TDD M3).
4. **Phase D (M2+, gated on the fun gate).** Build the **`CaveBackend`** and **`ScatterBackend`** *only after* low-sightline/open-field play proves fun at a gate — they are the most expensive additions and each carries its own determinism gotcha. Defer **WFC/cyclic-grammar** indefinitely unless a specific band demands them.

Throughout, the empty-principle/flavor socket profile stays as the permanent control, exactly as the all-off `RunConfig` does for oppositions.

## Open questions

- **How many backends to actually build vs. defer? (scope/effort — Director.)** The socket backend covers groups A, C2/C3, D, and E. CA (caverns/mazes) and scatter (open-field) are *each* a real subsystem with their own determinism gotchas. **Recommendation:** ship socket-only through M1; build CA and scatter **only when a specific band's low-sightline/open-field play proves fun at a playtest gate** ([b1](b1-open-field-with-cover.md)/[b3](b3-organic-caverns.md) both flag this). Don't pre-build backends on spec.

- **Grammar/WFC layer, or keep imperative stages? (effort/vision — Director.)** The TDD already rejected full grammar engines and pure-WFC; WFC's connectivity/homogeny problems make it overkill for our 2-cell sockets ([WFC mixed-pipeline study](https://www.researchgate.net/publication/348569324_Combining_Constructive_Procedural_Dungeon_Generation_Methods_with_WaveFunctionCollapse_in_Top-Down_2D_Games)). **Recommendation:** keep imperative composable stages; reserve a *single optional cyclic-loop principle* (the reserved `loop_back_count`, Unexplored-style) as the only grammar-flavored stage, and only if loops prove worth it. WFC stays a deferred backend behind the same interface.

- **Authoring cost of per-band profiles vs. payoff. (scope — Director.)** A `BandProfile` is more authoring surface than today's single config. Dead Cells justifies it because biome-dedicated pools + a graph spec *are* the content. **Recommendation:** adopt the profile (it's the only way bands-as-biomes become data per TDD M3), but keep profiles thin early — backend + archetype + pools, with principles/flavors added one at a time as content lanes.

- **Where do bands-as-biomes end and intra-band tiers begin? (design — Director; flagged in [d3](d3-layered-tiered.md).)** The "Layered/tiered" principle risks duplicating what swapping bands already gives. **Recommendation:** treat distinct *biomes* as separate `BandProfile`s (Band 1 vs Band 2), and reserve the `Layered` principle for a deliberate *two-tier* "front vs deep" feel **within** one band — prototype 2-tier only before committing to N-tier authoring cost.

- **Connectivity-carve vs. reject-and-retry for non-socket backends. (technical.)** CA/scatter/archipelago can produce disconnected floor; carving a connector is deterministic but alters the floor graph, while reject-and-retry (whole-build re-seed, the socket model) is simpler but can loop on pathological seeds. **Recommendation:** carve for CA (keep-largest + bridge), retry for socket (already proven) — make Stage 5 backend-aware.

---

**One-line summary:** Promote today's single socket generator into a **default backend + first stages of a data-driven `BandProfile` pipeline** (backend → archetype → ordered principle overlays → ordered flavor passes → connectivity guarantee → existing seal/grade/populate), so the existing band, the 19 explored archetypes/principles/flavors with their modifications, and future bands are all authored as `.tres` composing reusable stages — while the empty-flavor socket profile stays a byte-identical determinism control and the band→opposition handoff stays a clean data seam.

**Biggest Director-decision flag:** *How many generation backends to actually build vs. defer* — the socket backend (plus archetype/principle/flavor stages) covers most of the matrix for nearly free, but **organic caverns (CA) and open-field (scatter) each require a genuinely new backend with its own determinism gotcha**, so they should be built only after their low-sightline / open-space play proves fun at a playtest gate, not pre-built on spec.
