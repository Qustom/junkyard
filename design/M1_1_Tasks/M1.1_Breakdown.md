# THE FAR YARD — M1.1 Milestone Breakdown

**Companion to:** `Junkyard_M1_Breakdown.md` (M1.0), `M1_As_Built.md` (canonical APIs), `G4_findings.md` (the ITERATE verdict that triggered this milestone)
**Milestone:** M1.1 — Greybox Cost Axis (push-your-luck iteration)
**Status:** planning (Director review pending — no board items / dispatch yet)
**Purpose:** Iterate on the M1.0 greybox loop, which passed engagement but **failed its push/cash-out tension gate (G4 = ITERATE)**. Add a depth-scaled **cost/risk axis** so "push deeper vs. extract now" becomes a genuine push-your-luck decision, then **re-run the playtest gate** to test whether the tension is fun.

---

## 1. Milestone goal — the one thing M1.1 must prove

> **M1.0 proved the loop is engaging but degenerate:** 11 runs/session, ~18s median run, the carry/capacity decision works — but **30 extract / 2 death / 0 timeout**. There is a reward axis (deeper = better junk, B3) and **no cost axis**. With no cost to depth, "push vs. extract" is not a decision — it's always "push."

**The single thing M1.1 must prove:** that adding a **depth-scaled cost/risk axis turns "one more room?" into a real, felt, *fun* gamble** — i.e., that runs stop being uniform "push-to-the-end-then-walk-back-and-extract" and start showing a spread of outcomes (some extract early/safe, some push-and-die, some time out, some get lost) driven by player risk appetite, not by a single dominant strategy.

This is measured the same way M1.0 was — re-running G4's question (*is the push/cash-out tension fun?*) against the **same telemetry**, now with the risk systems live, so the two builds are **directly comparable**. The success signal is no longer "does the loop pull replays" (M1.0 already proved that) but **"is there now a real distribution of run outcomes and end-causes, and does the Director feel the gamble."**

M1.1 is the **first iteration of a kill/iterate loop**: M1.0 → M1.1 → (playtest) → M1.2 … Every M1.x version is designed to be **re-runnable and comparable** against its predecessors. This document is the **template** for future M1.x breakdowns.

---

## 2. Scope guardrails — what M1.1 is and is NOT

**M1.1 IS:**
- Still **greybox** — colored rects/shapes, no real art, no real audio (the M1 greybox asset norm in `M1_As_Built.md` §"Greybox asset norm" stands: implementing agents stub placeholders inline; no paid asset generation).
- Still **one band**, one currency (Money), the existing seeded proc-gen spine.
- **Four prototype opposition systems** (the Director chose all four — see §3) layered onto the existing M1.0 loop, each **fully configurable via data + a pre-run menu**.
- A re-run of the **same feedback gate** with config-marked telemetry so M1.0 vs M1.1 (vs future M1.x) are comparable.
- The fix for three **foundational bugs** (BUG1/2/3) that the analysis depends on.

**M1.1 is NOT:**
- **Not** the final M2/M3 implementations of these systems. The pursuing hazard is **not** the M2 enemy-AI vertical slice; the exposure meter is **not** the M3 exposure system; the maze risk is **not** full WFC/cyclic-loop generation. These are **throwaway-grade prototypes** that exist only to test whether a cost axis makes the loop tense. If the gate says "fun," M2/M3 build the real versions; if not, we cut/swap and re-gate.
- **Not** balanced/tuned to final numbers. Every knob ships **configurable, not balanced** — the whole point of the pre-run Config menu is that the Director sweeps values across playtest runs to find where the tension lives. Acceptance criteria are about **the knob existing and taking effect**, not about a specific value being "right."
- **Not** a scope expansion of the loop itself — no new bands, recipes, NPCs, save-system features, real economy workbook, or combat depth. Resist adding anything not on this task list; scope creep across four new systems is the top M1.1 risk (see §7).
- **Not** widening the locked telemetry contract: `run_ended(reason, duration_s, depth_reached)` arity stays fixed (`M1_As_Built.md` §Telemetry). New opposition data rides **new event types** and the `run_started` config snapshot, never a wider `run_ended`.

### Prerequisite
M1.0 must be on `main` and green (it is — `M1_As_Built.md` reflects `main` through M1 wave 5; only G4 was outstanding and is now recorded ITERATE). M1.1 builds directly on the M1.0 autoloads, the B3 depth model (`depth_index`/`depth_norm`/`dist_to_gate`), the §Telemetry contract, and `scenes/game/main_game.tscn`'s Start Run menu.

## 3. Workstreams overview

M1.1 has three workstreams, in dependency order:

**(a) Foundations** — the shared run-config data model, the pre-run Config menu, telemetry config-marking, and the three blocking bug fixes. Everything in (b) reads the run-config model and emits config-marked telemetry, so this lands **first**.
> `R0` run-config data model · `CFG` pre-run Config menu · `TEL` telemetry config-marking + per-opposition events · `BUG1` `duration_s` · `BUG2` within-band depth · `BUG3` open sockets to void

**(b) The four opposition systems** — the cost axis. All four ship in M1.1 (Director's call). Each is independently configurable and independently telemetried; each depends on `R0` (reads its config) and on the bug fixes that make its dimension real.
> `R1` pursuing/awakening hazard · `R2` costlier return trip · `R3` rising instability/exposure · `R4` maze/navigation risk

**(c) The re-gate** — playtest build assembly, telemetry analysis comparing config sweeps + M1.0 baseline, and the recorded verdict.
> `RG1` playtest build · `RG2` analysis + comparison · `RG3` the re-gate verdict

**Flow:** (a) is wave 1 (R0 strictly first, then CFG/TEL/bugs). (b) is wave 2, parallel worktrees once R0 + the relevant bug land. (c) is wave 3, after all of (b) integrates.

### Workstream (a) — Foundations

**R0. Run-config data model** — *the foundation everything else reads* · **assignee: game-director-designer** (data/Resource design) + **general-purpose** (the run-start wiring) · **dependsOn: none (wave-1 first task)** · **[GS]**
Define a single `RunConfig` Resource (`data/run_config/run_config.gd` + a default `.tres`) that holds **every opposition's knobs** as typed, sub-grouped fields (one sub-block per opposition R1–R4, each with an `enabled: bool` master toggle), plus a small "meta" block (seed override, build tag passthrough). It is the **one object the Config menu writes and every opposition system + `MainGame` reads at run start.** Wire `GameState.start_run()` (or a thin `MainGame` seam in front of it) to accept/hold the active `RunConfig` for the run, and expose it read-only to systems via the existing autoload surface (e.g. `GameState.active_run_config`). Default `.tres` = **all oppositions OFF** (so an unconfigured run reproduces the M1.0 baseline exactly — this is what makes M1.0 vs M1.1 comparable).
- *Knobs exposed:* the schema container for all of R1–R4's knobs + per-opposition `enabled` masters + seed override. (The individual knobs are defined by R1–R4's specs; R0 owns the *container shape* and the all-off default.)
- *Telemetry:* none itself — but it must be **serializable to a flat dict** for TEL to snapshot onto `run_started`.
- *Acceptance:* a `RunConfig.tres` loads; `GameState.active_run_config` is populated at run start; with the all-off default the loop behaves identically to M1.0 (no opposition active); the config serializes to a flat dict for telemetry.

**CFG. Pre-run Config menu** — *Director tunes each run before starting* · **assignee: ui-ux-designer** (Control layout/readability) + **general-purpose** (binding to `RunConfig`) · **dependsOn: R0** ·
A `Control` panel placed **next to the existing Start Run menu** in `scenes/game/main_game.tscn` that exposes **all** R1–R4 knobs from `RunConfig` (per-opposition collapsible section with its master on/off toggle + sliders/fields for magnitude, depth thresholds, rates, curves), writes them into the active `RunConfig`, and hands it to the run on Start. Greybox styling; readability + "which opposition is this" labeling matter because the Director tunes here every run. Must support a **"reset to M1.0 baseline (all off)"** action and show the current values at a glance. Does **not** restart dives — it only configures the next run launched from the existing Start Run flow.
- *Knobs exposed:* surfaces 100% of `RunConfig`'s knobs (R0 + R1–R4); no hidden/hardcoded opposition values.
- *Telemetry:* none directly (TEL snapshots the resulting `RunConfig`); optionally fires a local "config applied" for debugging.
- *Acceptance:* from `main_game`, the Director can toggle each opposition on/off and set every knob before pressing Start; the started run reflects those values; "reset to baseline" returns all-off; no opposition knob is unreachable from the menu.

**TEL. Telemetry — config marking + per-opposition events** — *make runs comparable + capture cost-axis behavior* · **assignee: qa-playtest-coordinator** (telemetry contract owner) · **dependsOn: R0; coordinates with R1–R4 for their event payloads** · **[EB]** (declares the new opposition event signals)
Extend the `Telemetry` autoload to (1) **snapshot the active `RunConfig` flat dict onto the `run_started` row's `data`** (additive payload field, like the existing `build` tag — **not** a schema bump, envelope unchanged), so every run records exactly which config produced it; and (2) add **per-opposition `EventType` constants + JSONL rows** for the four oppositions' events (see each R-task). Bump `TELEMETRY_SCHEMA_VERSION` only if a new envelope key is needed (the config snapshot does **not** require it — it rides `data`). **Do NOT widen the locked `run_ended(reason, duration_s, depth_reached)` arity** — new dimensions ride new rows. New end-causes (`timeout`, hazard-`death`, lost-`death`) continue to use the existing `run_ended.reason` string.
- *Knobs exposed:* an opt-in stays as-is (consent flow unchanged); optionally a per-opposition log verbosity flag (nice-to-have, not required).
- *Telemetry (this task defines the rows):* `run_started.data.run_config` = flat config snapshot; the new `EventType` constants for R1–R4 events (hazard_awoke / hazard_caught, return_cost_incurred, exposure_crossed / exposure_penalty, nav_branch_taken / nav_lost_proxy) — payloads coordinated with each R-task.
- *Acceptance:* a completed run's JSONL `run_started` row carries the full config snapshot; with an opposition enabled, its event rows appear in the log; with it disabled, they don't; `run_ended` arity is unchanged; schema version handled correctly.

**BUG1. `run_ended.duration_s` is always 0** — *the core gate metric* · **assignee: general-purpose** · **dependsOn: none (can land wave 1 alongside R0)** · **[GS]**
Fix `GameState` so `end_run(reason, duration_s)` reports the real run duration instead of 0 (run length is currently only recoverable via Telemetry `t_ms` — fragile, and the gate's headline number). Capture run start time at `start_run` and compute elapsed at every end path (extract / death / timeout).
- *Knobs:* none. *Telemetry:* makes the existing `run_ended.duration_s` meaningful (no new row).
- *Acceptance:* `run_ended.duration_s` equals real elapsed run time (within a frame) for extract, death, and timeout; cross-checked against `t_ms`; a GdUnit4 assertion covers it.

**BUG2. Within-band depth not tracked** — *the cost axis is depth-scaled, so depth must be real* · **assignee: general-purpose** · **dependsOn: none (wave 1)** · **[GS]**
`current_depth` is a band-entry counter stuck at 1; the B3 within-band model (`depth_index`/`depth_norm`/`dist_to_gate` on `PlacedPiece`) already exists but isn't reflected in run-state/telemetry. Track the player's **live within-band depth** (the `depth_index` of the piece they're in, and the max reached) in run-state, emit it on depth change, and feed it to `run_ended.depth_reached`. Every R-task's depth-scaling reads this; the whole M1.1 analysis ("how deep did they push under risk?") needs it.
- *Knobs:* none (it reads B3's existing `DepthCurve`/geometry). *Telemetry:* a `depth_changed(depth_index, max_depth)` row (or reuse an existing signal) + a correct `run_ended.depth_reached`.
- *Acceptance:* moving deeper updates live depth in run-state and telemetry; `run_ended.depth_reached` = the max within-band depth reached (not 1); R1–R4 can all read current depth at runtime.

**BUG3. Open sockets to off-map void** — *needed for the maze/nav opposition + general quality* · **assignee: environment-artist** (geometry/socket authoring) + **general-purpose** (generator cap) · **dependsOn: none (wave 1)** ·
Zone pieces leave open sockets into off-map void, letting the player walk off the playable area. Cap unused sockets with a wall/cap during generation (or author cap pieces) so the band is sealed. This is a **prerequisite for R4** (branching layouts and limited-vision navigation are only fair if the play space is bounded) and removes a quality issue that would confound the playtest.
- *Knobs:* none (correctness fix). *Telemetry:* none.
- *Acceptance:* a generated band has no open socket leading off-map; the player cannot walk into void on any seed in a determinism sweep; B2 determinism (`band.fingerprint()`) is preserved.

### Workstream (b) — The four opposition systems (the cost axis)

> All four read `GameState.active_run_config` (R0), scale off live within-band depth (BUG2), and emit config-marked telemetry (TEL). Each is independently on/off so the Director can isolate a single opposition or stack them. **Each opposition's internal spec becomes its own task artifact** (`design/M1_Tasks/R<n>_*.md`) authored by `game-director-designer` as the first step of that task — this breakdown sets the contract, not the internals.

**R1. Pursuing / awakening hazard** — *a thing that chases you the deeper/longer you go* · **assignee: general-purpose** (behavior) + **game-director-designer** (the R1 spec + config defaults) + **character-animator** (greybox "awake/chase" tell — a color/shape state, inline placeholder) · **dependsOn: R0, BUG2** ·
A greybox entity (or field) that **activates and pursues** as a function of depth and/or time-in-band: it "awakens" past a depth threshold or after lingering, then chases the player; catching the player triggers a `death` end-cause (routes through the existing `fail_run(&"death")`, pockets fraction applies). It is the most direct "deeper = more dangerous." Greybox: a colored shape that changes color when awake and moves toward the player. **Not** the M2 enemy-AI slice — pathing can be crude (toward-player steering / nearest-floor-cell), no combat, no health.
- *Knobs:* `enabled`; awaken trigger (`depth_threshold`, `linger_seconds`); chase speed (flat + optional per-depth scale); catch radius; whether catching kills outright vs. a cost; spawn count/scaling with depth.
- *Telemetry:* `hazard_awoke(depth, trigger)`; `hazard_caught(depth, run_t_ms)`; (catch → existing `run_ended.reason = death`).
- *Acceptance:* with R1 on, the hazard awakens per its threshold, visibly chases, and can end a run as `death`; with R1 off, no hazard exists and behavior matches M1.0; all knobs take effect from the Config menu; events log.

**R2. Costlier return trip** — *depth has an extraction cost, not a free walk-back* · **assignee: general-purpose** (mechanic) + **game-director-designer** (R2 spec + curve defaults) · **dependsOn: R0, BUG2** ·
Make the **way back scale with how deep you pushed**, so "fill inventory then stroll to the gate" stops being free. Prototype mechanism (the R2 spec picks/combines; all greybox): e.g. the return path lengthens or partially collapses behind you (one-way/decaying links past a depth), and/or a per-depth "egress toll" (a resource/clock cost incurred when retreating that scales with `dist_to_gate`). Reads B3's real `dist_to_gate` (works on branching layouts). The point is that **deeper pushes cost more to undo**, putting a real price on the last room.
- *Knobs:* `enabled`; mechanism select (lengthen / decay-behind / egress-toll); cost magnitude + per-depth curve; depth threshold where the cost starts; (if toll) which resource it taxes (clock vs. exposure vs. a dedicated meter).
- *Telemetry:* `return_cost_incurred(depth, cost_kind, magnitude)` on each retreat-cost event.
- *Acceptance:* with R2 on, retreating from depth `d` costs measurably more than from depth 1 (observable in-game + in telemetry), scaling with the configured curve; with R2 off, walk-back is free (M1.0 behavior); knobs take effect.

**R3. Rising instability / exposure meter** — *a baby version of the M3 exposure system* · **assignee: general-purpose** (meter + penalty) + **game-director-designer** (R3 spec + rate/threshold defaults) + **ui-ux-designer** (a greybox exposure readout in the HUD) · **dependsOn: R0, BUG2** ·
A meter that **climbs while you're deep and punishes lingering.** Rate scales with depth (deeper = climbs faster) and/or with time-in-band; crossing thresholds inflicts escalating penalties (e.g. speed/vision/clock penalties, or at max → forced `timeout`-style run loss). Hooks the existing `GameState.add_exposure`/meta `exposure` only if useful, but the **run-active meter is run-state** (disposable per dive) — it is a *prototype* of M3, not the persistent M3 system. This is the most direct counter to "linger deep and loot freely."
- *Knobs:* `enabled`; base climb rate; per-depth rate multiplier/curve; threshold levels + each level's penalty type & magnitude; whether max-meter forces run-loss (`timeout` cause) and the decay (if any) when retreating shallow.
- *Telemetry:* `exposure_crossed(level, depth, run_t_ms)` on each threshold crossing; `exposure_penalty(level, penalty_kind)` when a penalty fires; (max → existing `run_ended.reason = timeout`).
- *Acceptance:* with R3 on, the meter rises faster at depth, crossings fire penalties, and (if configured) max-meter ends the run as `timeout`; a greybox readout shows the meter; with R3 off, no meter/penalty (M1.0 behavior); knobs take effect.

**R4. Maze / navigation risk** — *deeper = genuinely harder to find the way back* · **assignee: general-purpose** (vision/fog + generator wiring) + **environment-artist** (branching layout via existing `branch_chance`, greybox fog/vision) + **game-director-designer** (R4 spec + thresholds) · **dependsOn: R0, BUG2, BUG3** ·
Make deeper areas **harder to navigate**, so "one more room" risks getting stuck and burning the clock/exposure. Two greybox levers, both configurable: (1) **branching layout** — raise the existing B2 `branch_chance` (currently `0.0` linear spine) as a function of depth so deep areas branch and dead-end; (2) **limited vision / fog** — a vision radius / fog-of-war that hides far geometry, optionally tightening with depth or exposure. Requires BUG3 (a sealed map) to be fair. "Lost" is hard to measure directly, so emit a **proxy** (backtracking / time-without-depth-progress / revisited-cells) for the analysis.
- *Knobs:* `enabled`; `branch_chance` base + per-depth curve; max branch/dead-end depth budget; vision radius (flat + per-depth/per-exposure tightening); fog on/off; lost-proxy thresholds.
- *Telemetry:* `nav_branch_taken(depth, junction_degree)`; `nav_lost_proxy(metric, value, depth)` (the chosen backtrack/no-progress proxy) — coordinate the exact proxy with TEL.
- *Acceptance:* with R4 on, deep areas branch and/or vision is limited per config, and the lost-proxy logs; the band stays sealed (BUG3) and deterministic (B2 fingerprint) for a given seed+config; with R4 off, layout is the linear M1.0 spine with full vision; knobs take effect.

### Workstream (c) — The re-gate

**RG1. Playtest build** — *the full loop with risk active* · **assignee: general-purpose** + **qa-playtest-coordinator** (build verification) · **dependsOn: all of (b) integrated, TEL** ·
Assemble a runnable greybox build of the M1.1 loop: `main_game` → Config menu (set oppositions) → Start → dive with risk active → push/extract/die/timeout/get-lost → bank/lose → sell → repeat. Verify the loop runs end-to-end with each opposition individually and with all four stacked, and that config-marked telemetry writes. Carry forward the M1.0 G3 loop-restart seam (`continue_pressed → start_new_run`).
- *Acceptance:* a fresh build runs the complete loop with oppositions on; each opposition can be toggled per run from the menu; telemetry logs config + opposition events; no blockers; multiple runs per session possible.

**RG2. Telemetry analysis + M1.0 comparison** — *did a cost axis change the outcome distribution?* · **assignee: qa-playtest-coordinator** · **dependsOn: RG1 + playtest data captured** ·
Analyze the playtest JSONL: end-cause distribution (extract/death/timeout) **per config**, run-length and max-depth distributions, per-opposition event frequencies, and a **side-by-side vs. the M1.0 baseline** (the all-off config reproduces M1.0, giving an in-build control). Surface which oppositions (alone or stacked) actually shifted behavior off the "push-to-end-then-extract" dominant strategy. Provide the evidence packet the gate needs.
- *Acceptance:* an analysis artifact comparing end-cause/run-length/depth distributions across configs and against M1.0, with a clear read on whether the cost axis created a real outcome spread.

**RG3. The re-gate verdict** — *is the tension fun now?* · **assignee: qa-playtest-coordinator** (assembles) → **Director** (decides) · **dependsOn: RG2** ·
Re-run G4's question (*is the push/cash-out tension fun?*) against the M1.1 build, backed by RG2's analysis. Produce `design/M1_Tasks/G4_findings_M1.1.md` (mirroring `G4_findings.md`) with a recorded **go / iterate / pivot** verdict. Per the orchestrator loop, the **Director decides**; the agent assembles evidence + a recommendation. A "go" advances to M2; "iterate" spawns M1.2 (swap/cut/re-tune oppositions using this same template); "pivot" is a deeper design call for the Director.
- *Acceptance:* a recorded go/iterate/pivot verdict in a `G4_findings_M1.1.md`-style doc, backed by config-marked telemetry, comparable to the M1.0 G4 finding.

## 6. Wave / build order (for the orchestrator)

The proven M1 process applies: parallel agents in `isolation: worktree`; **pre-declare every new `event_bus.gd` signal on `main` before a parallel wave** so no two worktree agents edit `event_bus.gd` at once; flag tasks that touch `game_state.gd`/`event_bus.gd`.

### Wave 1 — Foundations (R0 first, then the rest of (a))
**R0 lands strictly first and solo** — it is `[GS]` and defines the `RunConfig` container that all of (b) and CFG/TEL read. Treat R0 as a sequential foundation: merge it to `main` before opening the rest of wave 1, so CFG/TEL/R1–R4 all build against a stable config schema.

After R0 is on `main`, the rest of wave 1 can run in **parallel worktrees**, with one ordering constraint on the shared files:
- **`[GS]` tasks (BUG1, BUG2) touch `game_state.gd`.** R0 also touched it. To avoid two agents editing `game_state.gd` at once, run **BUG1 + BUG2 sequentially after R0** (or as a single combined `game_state.gd` pass), *then* fan out the rest. They're small and naturally adjacent (start-time capture + depth tracking).
- **CFG, TEL, BUG3 then run in parallel** (CFG = `main_game.tscn` + new UI scene; TEL = `telemetry/` + `event_bus.gd`; BUG3 = generator/zone-piece geometry — disjoint files).
- **Pre-declare on `main` before wave-1 parallel fan-out** (the `event_bus.gd` signals TEL + the bug fixes need), so `event_bus.gd` is edited once:
  - `depth_changed(depth_index, max_depth)` (BUG2)
  - *(TEL is the sole `event_bus.gd` editor for opposition signals — see the recommendation below; if TEL declares all R1–R4 signals up front in wave 1, the wave-2 oppositions never touch `event_bus.gd`.)*

> **Recommended:** have **TEL pre-declare ALL opposition event signals in wave 1** (hazard_awoke, hazard_caught, return_cost_incurred, exposure_crossed, exposure_penalty, nav_branch_taken, nav_lost_proxy) as the single `event_bus.gd` edit for the whole milestone. Then wave-2's R1–R4 each only *emit* existing signals and never touch `event_bus.gd` — maximum parallelism, zero collision.

### Wave 2 — The four oppositions (fully parallel worktrees)
With R0 + BUG2 + TEL's signals on `main`, **R1, R2, R3, R4 run in four parallel worktrees.** They are file-disjoint by design:
- R1 → a new hazard scene/script + reads config; emits pre-declared signals.
- R2 → return-cost system (likely a small run-state system + generator hook for decay-behind) + reads config.
- R3 → exposure meter (run-state system) + a HUD readout (ui-ux-designer) + reads config.
- R4 → generator `branch_chance` hook (environment-artist) + a vision/fog node + reads config; needs BUG3 (sealed map) on `main`.
- **None edit `event_bus.gd`** (TEL pre-declared the signals) and **none should edit `game_state.gd`** (R0's `active_run_config` + BUG2's depth are already the read surface; route any run-end through the existing `fail_run`/`extract_and_end_run`). If an opposition discovers it *must* touch `game_state.gd`, pull it out of the parallel set and sequence it — flag at brief time.
- Each opposition's first sub-step is its `game-director-designer` spec (`R<n>_*.md`); the programmer builds against that spec.

### Wave 3 — Re-gate (sequential)
RG1 (build assembly, after all four integrate) → playtest sessions (human) → RG2 (analysis) → RG3 (verdict, Director decides).

### Standing rules during all waves
- After each integration merge to `main`: `git push origin main`.
- Run the **wave close-out deviation sweep** (CLAUDE.md) after wave 1 and after wave 2 before dispatching the next — the Director dispositions every `DESIGN_DEVIATIONS.md` entry; reapply canonical reality into `M1_As_Built.md` / `M1_Design_Decisions.md`.
- Mirror every task status change to GitHub Projects.

## 7. Definition of done for M1.1

M1.1 is complete when:

1. A **`RunConfig` data model** holds every opposition's knobs; its all-off default reproduces the M1.0 baseline exactly.
2. A **pre-run Config menu** next to the Start Run menu exposes **all four oppositions' knobs** (on/off, magnitude, depth thresholds, rates, curves) and configures the next run; "reset to baseline" works.
3. **All four oppositions** (R1 pursuing hazard, R2 costlier return, R3 exposure meter, R4 maze/nav) are present, **configurable via the menu**, depth-scaled, and **independently telemetried**; with all off, the loop equals M1.0.
4. **BUG1/2/3** are fixed: `run_ended.duration_s` is real, within-band depth is tracked through to `run_ended.depth_reached`, and the band is sealed (no walk-off-map).
5. **Telemetry marks the active config** on `run_started` and logs each opposition's events, **without widening the locked `run_ended` arity**.
6. A **build runs the full loop with risk active** (each opposition individually and stacked), producing config-marked telemetry across runs.
7. The **re-gate playtest has run and produced a recorded go / iterate / pivot verdict** (`G4_findings_M1.1.md`), backed by config-marked telemetry and a side-by-side comparison against the M1.0 baseline.

As with M1.0, the deliverable is not just code — it is an **answer**: *does a depth-scaled cost axis make push-vs-extract a real, fun decision?*

## 8. How this version slots into the iterate loop

M1.1 is the first turn of the M1 **kill/iterate loop**:

```
M1.0 (loop) → G4 ITERATE  ──►  M1.1 (cost axis) → re-gate
                                      │
                          go ─────────┼───────── iterate ──► M1.2 (swap/cut/re-tune via this template)
                                      │
                                      └────────── pivot ──► Director-level design rework
```

Two design choices make every M1.x **re-runnable and comparable**:
- **The `RunConfig` + Config menu** make each run a labeled experiment; the **all-off config is a permanent in-build control** that reproduces the prior baseline, so a new opposition is always measured against "no opposition," not against memory.
- **Config-marked telemetry + the `G4_findings*.md` template** mean each version's verdict is recorded the same way and the numbers line up across versions (same end-cause/run-length/depth metrics).

**This document is the template for future M1.x breakdowns.** An M1.2 would reuse §1's "single thing to prove," §2's greybox/configurable-not-balanced guardrails, the foundations-first wave structure, and the re-gate workstream — changing only which oppositions are added, cut, or re-tuned based on the M1.1 verdict.
