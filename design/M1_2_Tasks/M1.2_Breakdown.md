# THE FAR YARD — M1.2 Milestone Breakdown

**Companion to:** `M1.1_Breakdown.md` (the template), `M1_As_Built.md` (canonical APIs), `G4_findings_M1.1.md` (the M1.1 playtest feedback that triggered this iteration)
**Milestone:** M1.2 — Greybox Cost Axis, Iteration 2 (**Legibility & Level Scale**)
**Status:** Phase 1 (breakdown) — authored 2026-06-19. Phase 2 (per-task designs) + Phase 3 (fresh-eyes open-question resolution) follow per `CLAUDE.md` → "Version breakdown authoring — the three-phase process."
**Purpose:** The M1.1 cost axis **half-landed** — R2 (egress toll) and R3 (exposure) produced the `timeout` losses M1.0 never had, proving the cost mechanics *can* shift outcomes. But the M1.1 playtest showed the build is **not legible or fair enough to judge "is the gamble fun":** levels are tiny and uniform, the most visceral opposition (R1 hazard) **never actually catches** (`hazard_caught = 0`), and the attritional oppositions (R2/R3/R4) fire **invisibly**. M1.2 makes the cost axis **legible and fair**, then re-gates.

---

## 1. Milestone goal — the one thing M1.2 must prove

> **M1.1 proved the cost axis is mechanically real but illegible/unfair:** R2/R3 produced 5 timeouts (vs M1.0's 0), but R1 caught 0× (too big, wall-sticks in 4-cell halls), levels clear in ~17 s (fixed 128×64 px rooms, hardcoded count), and R2/R3/R4 give the player no visual feedback. The gamble exists in the data but not on the screen.

**The single thing M1.2 must prove:** that with **legible feedback** (you can *see* the hazard close in, the exposure climb, the toll bite, the dark press in) and a **level scale worth traversing** (configurable room count + size so depth feels like a journey, not a 17-second sprint), the depth-scaled cost axis becomes a **felt, fun push-your-luck decision** — measured the same way as M1.0/M1.1 (config-marked telemetry, all-off = the permanent baseline control) so all three versions are directly comparable.

M1.2 is **not** new cost mechanics — R1–R4 stay. It is **fixing + making legible** what M1.1 built, plus the level-scale and telemetry-hygiene foundations a fair re-gate needs.

---

## 2. Scope guardrails — what M1.2 IS and is NOT

**M1.2 IS:**
- Still **greybox** (colored rects/shapes, inline placeholders; no paid asset generation), one band, one currency, the existing seeded proc-gen spine.
- **Fixes + legibility for the four M1.1 oppositions**, a **configurable level scale**, and **telemetry hygiene** — driven 1:1 by the `G4_findings_M1.1.md` triage (I1–I5 + BUG4).
- A re-run of the **same feedback gate** with config-marked telemetry so M1.0 / M1.1 / M1.2 are comparable on the same metrics.

**M1.2 is NOT:**
- **Not** new oppositions or a redesign of R1–R4's mechanics (the cost axis stays; we make it legible + fair).
- **Not** real art/audio, new bands, recipes, NPCs, save-system features, or combat depth.
- **Not** balanced/tuned to final numbers — every new knob ships **configurable, not balanced**. Acceptance is "the knob exists and takes effect," not "the value is right."
- **Not** widening the locked `run_ended(reason, duration_s, depth_reached)` arity. New data rides new event rows + the `run_started` config snapshot.

### Prerequisite
M1.1 on `main` and green (it is — `c4c71b8` + CFG input fix `1ac32c2`). M1.2 builds directly on the M1.1 autoloads, `RunConfig` + CFG menu, config-marked telemetry, the B2/B3 generator, the four oppositions, and `scenes/game/main_game.tscn`.

## 3. Workstreams overview (3 waves)

The driving dependency: **I1 (level scale) reshapes the spatial canvas every other fix is tuned against**, so it is the foundation; the spatial oppositions (hazard, vision) are retuned *after* the new room scale lands.

**(a) Wave 1 — Spatial & data foundation** *(land first)*
> `I1` configurable level scale (room count + size) · `BUG4` branch-rate-independent socket seal · `I5` telemetry hygiene (`duration_s`=0 + real build SHA)

**(b) Wave 2 — Oppositions retuned to the new canvas** *(parallel, after Wave 1 on `main`)*
> `I2` hazard fix (size, navigation, catch) · `I4` vision/fog rework (real occlusion + legible fog/lost) · `I3` R2/R3 visual cues

**(c) Wave 3 — Re-gate** *(sequential; RG2/RG3 after the human playtest)*

## 4. Task list (Phase-2 designs expand each; ids are stable)

> Each task gets its own design doc `design/M1_2_Tasks/<id>_*.md` in Phase 2 (research on the premise + pseudocode + Open Questions), then a Phase-3 fresh-eyes pass resolves the open questions (Director-review items flagged). Roles below are the **design author** (Phase 2) + the **builder** (the eventual implementation wave). `[touch]` flags shared files to watch.

### Wave 1 — Spatial & data foundation

**I1. Configurable level scale (room count + size + new larger pieces)** — *the headline; depth must feel like a journey* · **design: game-director-designer** · **build: general-purpose + environment-artist (new larger greybox pieces — Director-confirmed in scope 2026-06-19)** · **dependsOn: none** · `[touch: run_config.gd (new knobs), band_generator.gd / BandGenConfig, the piece catalog + new piece scenes, junk_placer.gd (Phase-3 loot-scale fix), CFG menu, TEL snapshot]`
> **Director disposition (2026-06-19):** M1.2 ships **room-size multiplier + room-count knob + newly authored larger/varied greybox pieces** (the Phase-3 "defer new pieces to M2" recommendation was overridden — the Director wants real spatial variety, not just a uniform zoom). `environment-artist` authors the new pieces (B1 sockets + floor/wall so B2/B3 grade them and BUG3/BUG4 seal them); `general-purpose` does the knobs + generator/CFG/`junk_placer.gd` wiring. See `I1_level_scale.md` §Director Disposition.
Expose **room count** (currently the hardcoded `target_piece_count` in the `BandGenConfig` `.tres`) and **room size** (pieces are fixed 8×4-cell / 128×64 px scenes) as **`RunConfig` knobs** the Director sweeps in CFG. Room size may be a cell-scale multiplier and/or a set of larger authored greybox pieces (the design doc decides). **All-off / default must reproduce the current M1.1 baseline** (default count + size = today's values), so it stays the permanent control. New knobs join the determinism key (`fingerprint(seed + config)`), the CFG coverage assertion, and the TEL `to_flat_dict()` snapshot.
- *Acceptance:* room count + size are settable from CFG and visibly change the generated band; default = current baseline; determinism preserved; CFG/TEL pick up the new knobs automatically.

**BUG4. Branch-rate-independent socket seal** — *bigger/branchier levels must stay sealed* · **design: game-director-designer** · **build: general-purpose** · **dependsOn: none** · `[touch: socket_sealer.gd]`
From M1.1 close-out W2-R4-1: at high R4 branch rates some seeds leave 2–6 floor cells facing void because `SocketSealer` caps only `band.open_sockets`. Cap **all** outward-facing perimeter floor edges (any floor cell whose outward neighbour is neither floor nor a mated doorway) so the seal is **branch-rate-independent**. Geometry-only pass; `band.fingerprint()` unchanged.
- *Acceptance:* a determinism+seal sweep at high branch rates shows 0 void-facing cells on every seed; fingerprint unchanged; existing seal/determinism tests green.

**I5. Telemetry hygiene** — *the next gate's data must be trustworthy* · **design: qa-playtest-coordinator** · **build: qa-playtest-coordinator** · **dependsOn: none** · `[touch: telemetry.gd / game_state duration path, systems/version.gd]`
Two found-in-data defects: (1) `duration_s` still logs `0.0` on a subset of M1.1 runs (correlated with all-off / fast extracts — a BUG1 edge regression); (2) the telemetry `build` id is frozen at a stale SHA (`852b6e2`) because `systems/version.gd` doesn't read the real HEAD. Fix both so the M1.2 re-gate's run-length + build separation are clean.
- *Acceptance:* every completed run logs a real `duration_s`; `run_started.data.build` reflects the actual build SHA; a headless check covers the duration path.

### Wave 2 — Oppositions retuned to the new canvas (parallel)

**I2. Hazard fix (size, navigation, catch)** — *the predator must actually catch* · **design: game-director-designer** · **build: general-purpose (+ character-animator for the greybox tell)** · **dependsOn: I1 (tune against the new room scale)** · `[touch: hazard_entity.gd/.tscn, main_game.gd spawn seam]`
`hazard_caught = 0` in the M1.1 playtest: the hazard is too large and `move_and_slide`-sticks in 4-cell halls, so it never reaches catch range; it also wakes at depth 0–1 (instant, on tiny levels). Shrink it, improve closing (anti-wall-stick steering / smaller body / speed- or depth-scaled catch radius), and re-tune the awaken threshold against I1's larger rooms. The kill *routing* (`fail_run(&"death")`) is fine — make the catch fire.
- *Acceptance:* with R1 on, the hazard visibly closes and **catches → `death`** at a fair rate; off = M1.0; knobs take effect; `hazard_caught` rows appear.

**I4. Vision/fog rework (real occlusion + legible fog/lost)** — *the dark must actually hide* · **design: game-director-designer** · **build: general-purpose (+ environment-artist for the greybox look)** · **dependsOn: I1 (radius vs new room scale)** · `[touch: vision_fog.gd/.tscn, lost_proxy.gd, maybe a HUD "lost" cue]`
M1.1's `CanvasModulate`+`PointLight2D` only *dims* — the player can still see "darkened" geometry; fog-of-war and the `nav_lost_proxy` have no on-screen meaning. Make vision **occlude** (hide, not dim) beyond the radius, give fog memory a clear read, and surface a legible **"lost"** cue tied to `lost_proxy_threshold`. Radius tuned to I1's room scale.
- *Acceptance:* beyond the vision radius geometry is hidden (not faintly visible); fog memory + a lost cue are legible; off = full M1.0 vision; determinism/seal intact (pairs with BUG4); knobs take effect.

**I3. R2/R3 visual cues** — *attrition must be visible* · **design: ui-ux-designer** · **build: ui-ux-designer** · **dependsOn: none (R2/R3 already emit the signals)** · `[touch: HUD scenes/scripts (decision_hud / exposure_readout), hud_strings.csv]`
R2/R3 fire mechanically but invisibly. Give R3 a **prominent exposure bar** with threshold ticks + a **penalty flash** on each crossing; give R2 a **clock-toll pulse** + a **retreat-cost indicator** when the egress toll bites. Pure projection of existing signals (`exposure_meter_changed`/`exposure_crossed`/`exposure_penalty`, `return_cost_incurred`) — no new game state, ideally no new EventBus signals (if a cue needs one, pre-declare it the M1.1 way).
- *Acceptance:* the player can see exposure climbing + each penalty, and feel/see each retreat toll; off = M1.0 HUD; legibility holds the E2 readability rules.

### Wave 3 — Re-gate

**RG1. M1.2 playtest build + verify** · **build: general-purpose + qa-playtest-coordinator** · **dependsOn: all of Wave 1 + Wave 2 integrated** — assemble the runnable M1.2 loop, verify each fix + all stacked, config-marked telemetry writes. Template: `RG1_playtest_build.md`.

**RG2. Telemetry analysis vs M1.0/M1.1 baselines** · **qa-playtest-coordinator** · **dependsOn: RG1 + human playtest** — end-cause / run-length / depth distributions per config, side-by-side vs M1.0 (all-off) and M1.1; did legibility + level scale create a real, *felt* outcome spread? Template: `RG2_telemetry_analysis.md`.

**RG3. Re-gate verdict** · **qa-playtest-coordinator assembles → Director decides** · **dependsOn: RG2** — record go/iterate/pivot in `G4_findings_M1.2.md` (mirrors M1.1). go → M2; iterate → M1.3 (this template); pivot → design rework.

> The Wave-3 re-gate tasks reuse the M1.1 `RG{1,2,3}_*.md` specs as their template; their M1.2 design docs are authored when Wave 3 approaches (they depend on what Waves 1–2 actually built). The **Phase-2 design fan-out covers the six build tasks: I1, BUG4, I5, I2, I4, I3.**

## 6. Wave / build order (for the orchestrator)

The proven M1.1 process applies: parallel agents in `isolation: worktree`; **pre-declare any new `event_bus.gd` signal on `main` before a parallel wave** so no two worktree agents edit it; **single-writer-per-`.gd`-file** (the W1.1-2 lesson — watch `run_config.gd`, `band_generator.gd`, `main_game.gd`, the HUD scenes); push `main` after every merge; mirror task status to the board; run the **wave close-out deviation sweep** after each wave (Director dispositions).

- **Wave 1:** I1 owns the `run_config.gd` schema additions (new level knobs) — land I1's schema first if BUG4/I5 turn out to read it (they don't, so all three can run parallel; confirm at brief time). I1 also touches `band_generator.gd`; BUG4 touches `socket_sealer.gd`; I5 touches `telemetry.gd`/`version.gd` — file-disjoint, parallel.
- **Wave 2:** I2 (`hazard_entity` + `main_game.gd` spawn seam), I4 (`vision_fog`/`lost_proxy` + possibly `main_game.gd`), I3 (HUD) — **watch the `main_game.gd` collision between I2 and I4** (both may edit the dive-scene wiring, the W1.1-2 pattern); if so, sequence them or split the seam. I3 is HUD-disjoint.
- **Wave 3:** RG1 (assembly) → human playtest → RG2 → RG3.

## 7. Definition of done for M1.2

1. **Level scale is configurable** (room count + size) from CFG; default reproduces the M1.1 baseline; determinism preserved.
2. **The hazard catches** — R1 can end a run as `death` at a fair rate; `hazard_caught` rows appear.
3. **Every opposition is legible** — exposure climb + penalties visible; retreat toll visible; vision actually occludes; fog + "lost" readable.
4. **BUG4** — bands stay sealed at any branch rate. **I5** — `duration_s` is real on every run and the build SHA is accurate.
5. **A build runs the full loop** with the fixes (each individually + stacked), producing config-marked telemetry across runs.
6. **The re-gate playtest has run and produced a recorded go / iterate / pivot verdict** (`G4_findings_M1.2.md`), comparable to M1.0 and M1.1.

As with M1.0/M1.1, the deliverable is an **answer**: *now that the cost axis is legible and the levels are worth traversing, is push-vs-extract a real, fun gamble?*
