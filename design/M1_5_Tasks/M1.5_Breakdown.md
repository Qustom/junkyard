## 1. The one thing M1.5 must prove

M1.4 gave the run stakes + variety, and Wave 5 made the loop hold (the spawn-kill is gone, the pursuer is visible, the
camera reads). But the playtest exposed the danger as **something you can only run from, never answer**, the pursuer as
an **incomprehensible always-on chaser**, and two **legibility bugs** that nag every run (the money readout is hidden
behind the inventory; the grab prompt is always on screen). **M1.5 gives the player agency against danger — you can
*highlight an inventory item and throw it* to kill a pursuer — makes the pursuer a comprehensible, room-bound threat (a
slow patrol that only chases inside its spawn room), and fixes the two legibility bugs — then re-gates for a possible
"go."**

## 2. Scope guardrails (what M1.5 is and is NOT)

- **Greybox + configurable-not-balanced**, exactly as M1.1–M1.4. The two new *levers* (throwing, spawn-room pursuer) are
  swept `RunConfig` knobs whose *values* are the Director's to sweep; the thrown item reuses the existing `JunkPickup`
  greybox look; the pursuer behaviour is a config branch on the existing greybox `HazardEntity`, not new AI/navmesh.
- **The all-off `RunConfig` default stays the permanent baseline control** (determinism fp=`e943ac9c8bc1`, telemetry
  comparability with M1.0→M1.4). Every new *lever* knob defaults **off/neutral** so an unconfigured run still reproduces
  M1.0 byte-for-byte; the fun values ship in `make_default_play_preset()`, never by changing the code-level all-off
  defaults. This is the load-bearing carried contract.
- **The two HUD/interaction bug-fixes (L3 money-text, L4 grab-prompt) are NOT knob-gated** — they are correctness fixes
  that change behaviour for everyone (like Wave-5's BUG7/BUG8), not new levers. They do **not** touch generation, so they
  do not move the fingerprint.
- **NOT** new bands/art, a generator change, a meta/economy change, real enemy AI, or a save-schema change. Throwing and
  the highlight selector are **pure run-state** (remove an item from `run_inventory`, spawn a transient projectile) — **no
  meta persistence, no save bump**. The pursuer change is a behaviour branch + run-state, no save change.
- `run_ended` arity stays locked; telemetry stays additive (`data` fields only). Config-marked telemetry continues; the
  re-gate compares M1.5 cohorts to the M1.0/M1.1/M1.2/M1.3/M1.4 baselines on the same metrics.

## 6. Cross-cutting contracts (carried from M1.1–M1.4)

- **Configurable lever knob + config-marked telemetry**, all-off default reproduces the prior baseline as the permanent
  control. Every new lever knob joins `RunConfig.to_flat_dict()` + the CFG coverage assertion; update
  `tests/test_run_config.gd` / `tests/test_config_menu.gd` knob counts (current **81** → new count L0 sets). The throw +
  pursuer-behaviour knobs default **off/neutral**; the all-off control's fingerprint stays byte-identical (`e943ac9c8bc1`).
- **The default play-preset is a separate artifact** (`make_default_play_preset()`), NOT the code-level all-off default.
  The M1.5 fun stack layers throw-on + spawn-room-pursuer-on atop the M1.4 preset.
- **Throw + highlight are pure run-state** — removing an item from `run_inventory` and the transient projectile never feed
  `fingerprint()` and never persist. A missed throw re-enters the world via the existing `EventBus.junk_dropped` →
  `JunkSpawner` re-spawn path (reuse, don't reinvent).
- **No save-schema change in M1.5** (no new persisted meta). If Phase 2 surfaces any persistence need, that's a flag to
  the Director, not a silent bump.
- **`run_ended` arity locked**; telemetry additive only (new `data` fields / new signals, never an arity change).
- **Single-writer-per-`.gd`-file** within a wave; **pre-declare every new EventBus signal on `main`** (L0 does this for the
  whole milestone up front). **Parallel agents in `isolation: worktree`**; verify each branch's topology before merge (the
  qa-agent `git switch` leak — orchestrator memory); push `main` after every merge; mirror task status to the board; run
  the wave close-out deviation sweep (Director dispositions) after every wave.

## 7. Open risks to resolve in Phase 2/3 (per-task designs author these; fresh-eyes/Director ratify)

- **Throw selector ownership & input routing (L1):** where does the highlighted-index state live (`inventory_panel.gd`?)
  and how does the throw action read it cleanly — direct reference from `main_game`/player, or an EventBus `throw_requested`
  signal? The remap binds **F to both `interact` and `extract`** — confirm a single F press at a gate doesn't fire *both*
  actions in a conflicting way (prefer extract at a gate); confirm no other consumer relied on Q/E/Space.
- **Thrown projectile shape & collision (L1):** Area2D vs CharacterBody2D; collision layers/masks to detect the **pursuer**
  (`hazard` layer) vs **walls** (`world`); how "kill the pursuer" despawns it (the R1 hazard has no health — `queue_free`);
  does a throw-kill of the R1 pursuer reuse `new_hazard_killed(&"pursuer",…)` or want its own signal? Max range vs lifetime
  for the miss → re-drop; where the projectile parents so it's cleared with the band.
- **Throw vs the K5 hazards (L1):** does Space-throw also kill the ping-pong / bomb / spike hazards, or only the R1
  pursuer? (Director feedback names "pursuer" specifically — confirm scope; recommend pursuer-only for RG1, others a
  later sweep.)
- **Spawn-room bounds for the pursuer (L2):** how does the entity know "its spawn room" — does `setup()`/`spawn_ctx`
  already carry the room/piece bounds (the K5 pattern), or must `main_game.gd` pass them (the `main_game.gd` seam above)?
  What is "patrol" precisely — pace between two points, random walk within bounds, or idle-pivot — at what speed relative
  to chase? Re-entry behaviour (player leaves then returns to the room): resume chase immediately?
- **Highlight visuals (L1):** how the highlight reads against the existing `inventory_cell` styling (border vs tint), the
  default highlight when items exist, and the empty-inventory case.
- **Knob set (L0 pre-declares):** the exact names/defaults for the throw group (`throw_enabled`, `throw_speed`,
  `throw_max_range`/`throw_lifetime_s`, maybe `throw_kills` scope) and the pursuer group (`r1_spawn_room_only` +
  patrol-speed/params) — Phase 2 defines, L0 freezes the list + the new knob-count, contiguous-prefix house style
  (`throw_`, `r1_`).

## Phase 3 Dispositions & Phase 4 Lock (2026-06-24 — design LOCKED)

Phase 2 (per-task designs) + Phase 3 (fresh-eyes resolution) complete; each task doc carries a `Resolved Decisions
(Phase 3)` section. The Director dispositioned the flagged fun/scope calls. The design is now **locked + wired** — build
waves may begin.

**Director verdicts (FINAL):**
- **Throw kill scope = pursuer + ping-pong** — a thrown item kills **any `hazard`-layer body it overlaps** (the R1
  `HazardEntity` pursuer + the K5 ping-pong bouncer), for free, with **no scope knob**. The bodiless K5 bomb + spike stay
  un-throw-killable (out of scope; they're stationary/anchored). Item is destroyed on a kill; a miss re-drops it.
- **Pursuer patrol pattern = pace between two endpoints** within its spawn room, at a configurable slow speed
  (`r1_patrol_speed`, preset-swept ≈ half of chase). `r1_patrol_speed=0` collapses to idle-pivot. No `r1_patrol_pattern`
  knob. Chases iff the player is in the spawn room (`_room_bounds.has_point`), catch only while chasing, immediate
  re-entry resume; empty-bounds fail-safe = chase-everywhere.
- **Ship the `hazard_pursuer_state` telemetry signal** (cheap, additive; RG2 wants pursuer-state counts).
- **Keep the "Holding:" haul text verbatim** (`tr("HUD_HOLDING")`) — no "$"/coin glyph (a separate content change, not bundled into L3).
- **Leave the grab prompt up during a rejected-pickup flash** (item stays grabbable) for RG1.

**Locked contract reconciliations (L0 the build task MUST implement these exact names):**
- **Current knob count = 81** (72 `@export var` + 9 `@export_enum`; no `@export`-vs-CFG-row gap). **M1.5 adds 8 → final 89** (as-built; the earlier "88" was an arithmetic slip — 81 + 8 = 89).
- **Throw knobs:** `throw_enabled:bool=false`, `throw_speed:float`, `throw_max_range:float` (the miss rule; an in-script
  lifetime constant is the hidden fallback — NOT a knob). No `throw_lifetime_s`, no `throw_kill_scope` (scope is fixed).
- **Pursuer knobs (existing `r1_` group):** `r1_spawn_room_only:bool=false`, `r1_patrol_speed:float=0.0`.
- **L5 K5 kill toggles:** `hpp_kills:bool=true`, `hbomb_kills:bool=true`, `hspike_kills:bool=true` (default `true` = today's
  lethal behaviour; the lone non-`false` LEVER defaults, contract-*preserving*).
- **New EventBus signals (L0 declares; owners emit):** `item_thrown(item_id: StringName, depth: int, run_t_ms: int)`,
  `throw_missed(item_id: StringName, depth: int, run_t_ms: int)`, `throw_killed_hazard(item_id: StringName, kind:
