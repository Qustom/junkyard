# Worklog — FB7: telemetry for new_hazard_killed (K5a/b/c)

- **Task:** FB7 (M1.4 follow-up to FB6). Wire `EventBus.new_hazard_killed` into Telemetry so the three
  new M1.4 hazards' kills are attributable in the log (the gap surfaced while doing FB6).
- **Milestone:** M1.4 (post-Wave-5 follow-up).
- **Assignee:** Claude (orchestrator, direct micro-change — too small for a subagent).

## Root cause
ping-pong/bomb/spike (K5a/b/c) emit `new_hazard_killed(kind, depth, run_t_ms)` on a fatal hit, then route
death through `GameState.fail_run("death")`. Telemetry subscribed to `hazard_caught` (R1) but NOT
`new_hazard_killed`, so a death by one of the new hazards logged only a bare `cause=death` run_ended with
no attribution.

## What changed
- `systems/telemetry/telemetry_schema.gd` — new additive type `NEW_HAZARD_KILLED = "new_hazard_killed"`
  (+ in `ALL_TYPES`). **SCHEMA_VERSION stays 1**.
- `systems/telemetry/telemetry.gd` — connect `EventBus.new_hazard_killed` → `_on_new_hazard_killed`,
  emitting `{kind, depth, run_t_ms}` and flushing. Parallel to `_on_hazard_caught` (precedes the death
  run_ended, stamps run-elapsed itself).
- `tests/test_telemetry_jsonl.gd` — `_drive_run` emits `new_hazard_killed(&"spike",2,0)` on a death run;
  added an assertion that a `new_hazard_killed` row exists carrying `kind`/`depth`/`run_t_ms`.
