## BUG10 — root cause
`MainGame.start_new_run()` resolves the run's config into a local `run_cfg`, then calls
`_place_gate(band, spawn_pos)` at step 4. But `_place_gate` read `GameState.active_run_config`,
which is **null at that point**: `end_run()` sets `active_run_config = null` (game_state.gd:294),
and `start_run()` doesn't re-stage it until step 6 (after `_place_gate`). So `_place_gate` always
hit the all-off branch (`rc == null`) → a single fixed gate at the spawn offset, **regardless of
the exit_* config**. The `run_started` telemetry snapshot still showed `exit_enabled:true` because
that snapshot is taken from the staged `run_cfg` later — which is why FB5's unit test (it set the
config directly and called the placement helpers) passed while the live path was broken.

## BUG10 — fix
- `scenes/game/main_game.gd` — `_place_gate(band, spawn_pos, rc)` now takes the config explicitly;
  `start_new_run` passes the freshly-resolved `run_cfg`. No read of the (cleared) global.
- `tests/test_exit_placement.gd` — updated call sites to pass the config; added case **(f)**: with
  `active_run_config = null` (the live post-`end_run` state), passing an exits-on rc still places the
  full multi-gate count — a direct regression for the live bug.
- `tests/test_exit_placement_count.gd` — updated call sites to the new signature; corrected the FB5
  success message (placement MATH was always correct; the live "exits never spawn" report was BUG10,
  a wiring bug — not a math defect).
